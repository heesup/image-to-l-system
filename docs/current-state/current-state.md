| **Stage 3 conditioning: the ladder, visibility and depth all come back NEGATIVE** | ✅ SETTLED 2026-09-18 | Three independent probes, no training, all pointing the same way. **(1) Resolution does not help.** Held-out R² over the mean phytomer latent: position-only (no image) **+0.011**, token@224 (75 mm/cell) **−0.245**, token@448 (37.5 mm/cell) **−0.232**, ROI 12 cm crop at **0.54 mm/px** **−0.125**. Doubling the feature grid changes almost nothing and a crop ~140x finer than a token is still worse than predicting the mean. **(2) Occlusion is not the cause.** 53.4% of organs contribute zero pixels, but restricting the probe to VISIBLE organs *lowers* latent R² (0.057 → 0.036); occluded organs are slightly more predictable, sitting deep in large canopies. A visibility-weighted shape loss is not worth building. **(3) Depth is redundant here.** rgb 0.057, depth(plant-norm) 0.032, rgb+depth 0.055 — no gain. **(4) Contrastive would start from chance:** through the best learned linear map, a node's feature cannot pick its own organ out of its own plant's organs (0.027 vs 0.041 chance on visible latents), and that retrieval score is exactly what InfoNCE optimises. **Conclusion: per-organ shape is not present in a single nadir view at any resolution tested.** Petiole curvature, three leaflet orientations and four reproductive slots are simply not observable from directly above. The implication is to stop trying to make Stage 3 deterministic and lean on the generative readout it already has — get the *distribution* right (spread, hull, boundary) and let refinement choose — rather than to chase finer conditioning. What the probes do show is decodable: node POSITION (R² 0.27, and 0.34 for occluded nodes), which is why the scaffold is the healthy part of the model. ## Terminology

| term | meaning |
| :--- | :--- |
| **rasterised** | the input appearance produced by `HeliosPyTorchRenderer.render_mesh` — our own nvdiffrast pass, per-organ flat colours, no shadows or texture. This is what `generate_cache.py` writes and what the training render loss is computed with, so it is **in-domain by construction**. Called "flat" before 2026-09-20. |
| **raytraced** | the input appearance produced by Helios's C++ radiation renderer via `render_helios_eval_crops.py` — textured soil, shading, cast shadows. **Out-of-domain.** Called "Helios" before 2026-09-20, which was ambiguous because the rasteriser's own class is `HeliosPyTorchRenderer`. |
| **bulk parameters** | plant-scale outputs: days after planting, phytomer count. The paper's term; formerly "Stage 1 / Macro". Training log prefix `[Bulk]`. |
| **phytomer parameters** | per-phytomer outputs: position, rotation, scale and the shape latent. **Predicted TWICE, as a cascade** — not merged into one computation. The coarse stage predicts them directly (`[Phytomer]`, supervised by `loss_phytomer_pos` and friends, which are ungated and active in every run); that prediction then becomes the flow's conditioning; the flow predicts them again (`[Phytomer flow]`, velocity loss) and **its output replaces the coarse one at sampling** (`sample_ode` keeps the coarse values only as `stage2_*`). What `--stage3_geometry` changed was giving the flow geometry to predict at all — before it, the flow carried only the latent and the coarse geometry was final. |
| **render** | assembly through the frozen PhytomerVAE to a 14-D part tensor and mesh, then the rasteriser or Helios. Formerly "Stage 4". Log prefix `[Render]`. |
| **test-time fit** | the 200-step refinement. **Not a stage** — it re-solves the *same* phytomer parameters against the observation, so the forward pass and the fit are two mechanisms for setting one quantity. Formerly "Stage 4 refinement". |
| **relative** | Stage 3 flow state `[dpos(3) \| roll(2) \| scale(3) \| latent]`; a node decodes as `pos = parent + dpos`, so its parent must be resolved first. Called "plain" before 2026-09-20. |
| **absolute** | Stage 3 flow state `[pos(3) \| rot6d(6) \| scale(3) \| latent]` (`--stage3_absolute`); a node consults no other node. |
| ~~**merged**~~ | **Retired 2026-09-21 — the word carried two meanings and neither survived contact with the code.** It was used for `--stage3_geometry` (the flow predicts geometry), which every checkpoint in the lineage has; and it was read as "the two geometry predictions became one", which **has never been built or tested**. The coarse stage still predicts position, roll and scale in every run (`pos_head`/`roll_head`/`scale_head` are live, `loss_phytomer_pos` is ungated) and the flow overwrites that at sampling. Use the two precise terms below instead. The `merged_*` run names are historical and mean `absolute_*`. |
| **`--stage3_geometry`** | the flow predicts geometry, not only the shape latent. On in every current checkpoint. Worth **+4.26 raytraced refined** over the latent-only alternative (2026-09-20 re-measurement). |
| **coarse geometry heads** | `pos_head` / `roll_head` / `scale_head` on the coarse stage, predicting the same quantities the flow then overwrites. **Never removed, never ablated.** The 2026-09-12 design (§485) proposed dropping them once the flow carried geometry; only the first half shipped. They are not dead weight — the render loss trains them directly and their output is the flow's conditioning — but whether the duplication earns its keep is unmeasured, and there is no flag to turn them off. |
| **run** | one branch of an experiment. Never "arm". |
| **node position** | a per-phytomer slot Stage 2 predicts and the matcher pairs with a GT phytomer. Never "anchor". |

**On stage numbers.** The architecture is named by the **scale of parameter** each part produces —
`bulk parameters → phytomer parameters → render` — which is the paper's own vocabulary, so code,
documents and publication agree. Numbering was never stable (Stage 0–4, then "Stage 2+3" once two
of them shared a flow state, and a three-stage reading elsewhere) and it hid two things: only three
parts are learned (the image encoder and the VAE are frozen, the render is deterministic, the fit
has no parameters), and refinement is not a stage at all. Documents dated before 2026-09-20 use the
old numbering and are left as written; map them with the rows above. The CLI flags and checkpoint
argument keys (`--stage3_geometry`, `--stage3_absolute`) keep their names — renaming them would
break every existing checkpoint's stored args.

Report results from the **raytraced** column when comparing architectures or training recipes; the
rasterised column is in-domain and both fails to separate them and rewards memorising the eval set.
Rasterised remains fine for anything acting on geometry after the image is consumed — refinement
step count, optimiser, regularisation weights.
